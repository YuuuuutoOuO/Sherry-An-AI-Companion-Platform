## 三、技術領域

本發明係關於人工智慧（AI）對話系統與大型語言模型（LLM）之應用。具體而言，係關於在有限 GPU 記憶體（VRAM）之資源受限環境中，對多個大型語言模型（含本地推論模型與雲端 API 模型）之推理任務進行排程、資源互斥、動態降級與雲地混合調度之方法及系統；並同時涉及一種具自主社交行為之 AI 虛擬角色之插話時機判斷、群組話題萃取與長期記憶管理方法。

## 四、背景技術與欲解決之技術問題

### 4.1 背景技術

在既有技術中，建置一個可即時對話之 AI 虛擬角色（例如在即時通訊群組中之 AI 機器人），通常採用「單一模型、單一後端」之架構。此類架構將被動回覆、主動插話、背景話題分析、定時發言、語音對話、圖片生成等任務全部交由單一模型依序處理。

### 4.2 欲解決之技術問題

| 編號 | 技術問題 |
|------|----------|
| P1 | **單點資源瓶頸**：單一模型肩負多種任務時，推理佇列壅塞，即時對話之首字延遲（TTFT）顯著上升，使用者體驗劣化。 |
| P2 | **VRAM 競爭**：本地 GPU 同時運行多模型（LLM 推論、STT/TTS 語音、圖片生成）時易超載而推論失敗或當機；既有技術多採固定模型組合或簡單二元互斥鎖，無法依任務類型動態調度有限顯存。 |
| P3 | **雲地混合調度困難**：既有技術未區分「不佔本地資源之雲端模型」與「受 GPU 約束之本地模型」，導致本地任務被雲端任務阻塞，或雲端任務被本地鎖拖慢，算力利用率低落。 |
| P4 | **AI 缺乏自主社交行為**：既有聊天機器人多為純被動回應，無法判斷「何時適合主動加入群組對話」，亦無法追蹤群組話題之興衰。 |
| P5 | **重試策略僵化**：模型推論失敗時既有技術多半以相同模型重試，忽略改以更輕量模型換取服務可用性之可能性。 |

## 五、發明內容

### 5.1 技術手段總述

本發明提供一種多模型 AI 推理排程方法與系統，其核心技術手段包含六個特徵：

| 特徵 | 代號 | 內容 |
|------|------|------|
| 優先權佇列 | F1 | 將推理任務依類型分類並賦予權重，以非同步優先權佇列依序分派 |
| 事件式資源互斥 | F2 | 以狀態旗標＋非同步事件（asyncio.Event）實作 VRAM 互斥，事件通知喚醒、零輪詢 |
| 雲地混合調度 | F3 | 依模型前綴判斷本地/雲端；雲端並行不取鎖，本地序列化執行 |
| 動態降級 | F4 | 本地模型重試時自動切換至輕量快速模型，維持服務不中斷 |
| 話題萃取與遺忘 | F5 | 輕量 LLM 週期萃取群組話題並賦權重，強化/衰減模擬遺忘曲線 |
| 插話時機評估 | F6 | 分類器模型對對話快照評分，配合冷卻與次數上限決定主動插話 |

### 5.2 功效

1. 降低即時對話首字延遲（TTFT）——透過 F1 優先順序保證與 KV Cache 駐留。
2. 避免 GPU 顯存超載——透過 F2 事件式互斥，保證任一時刻僅單一顯存大戶任務執行。
3. 提升運算資源利用率——透過 F3 雲地混合調度，充分利用雲端算力。
4. 提升服務韌性——透過 F4 動態降級，單一模型故障不致服務中斷。
5. 更自然之 AI 社交行為——透過 F5/F6 使 AI 融入群組對話節奏。

### 5.3 發明之技術效果摘要（供撰寫摘要用）

本發明藉由「任務優先權分級 + 事件式 VRAM 互斥 + 雲地異質調度 + 重試降級」四層機制，在一張消費級/企業級 GPU 上同時穩定運行多個 LLM 服務；並輔以話題遺忘與插話評估機制，實現具自主社交行為之 AI 虛擬角色。

### 6.2 實施例一：多模型推理排程（主案）

**（A）優先權佇列（F1）**

每一推理任務定義為一資料結構（InferenceTask），至少包含：任務 ID、優先權權重、目標模型、系統提示詞、使用者提示詞、回呼函式（callback）。任務依任務類型分配優先權，典型權重如下：

| 優先順位 | 任務類型 | 權重 |
|----------|----------|------|
| 最高 | 被動回覆（TAG_RESPONSE） | 1 |
| 高 | 主動插話（INTERJECT） | 10 |
| 中 | 排程主動發言（HEARTBEAT） | 20 |
| 低 | 背景話題萃取（VIBE_UPDATE） | 50 |
| 最低 | 圖片生成（DRAW）／閒置爬蟲（WEB_EXPLORER） | 80 / 99 |

佇列採非同步優先權佇列（asyncio.PriorityQueue），任務以（權重, 序號）為鍵，權重愈小愈先執行；同權重者依序號先進先出。被動回覆以最小權重保證其最優先，確保使用者等待時間最短。

**（B）事件式 VRAM 互斥（F2）**

系統為每一種佔用顯存之異動（圖片生成、語音模式）建立一對狀態旗標與非同步事件：

- 圖片生成開始 → 旗標設為 True、事件清除（clear）。
- 圖片生成結束 → 旗標設為 False、事件設定（set）。
- 本地 LLM 推理任務於執行前執行 `await event.wait()`：事件被清除（即有其他顯存大戶任務運行中）時自動阻塞；事件被設定後由事件迴圈立即喚醒放行。

**相較於傳統互斥鎖（Lock）或輪詢（Polling）等待，本機制之差異**：事件就緒時由事件迴圈直接喚醒等待任務，**無需 CPU 輪詢空轉**；且事件可被「多個 LLM 推理」與「單一外部顯存任務」共享，天然支援 N：1 之資源群互斥，不需為每條推理佇列個別加鎖。

**（C）雲地混合調度（F3）**

任務分派時，依模型字首（prefix）判斷模型所在後端：

| 後端 | 前綴 | 資源屬性 |
|------|------|----------|
| Ollama（原生 API） | `ollama:` | 本地 |
| LM Studio（OpenAI 相容） | `lms:` | 本地 |
| vLLM | `vllm:` | 本地 |
| OpenAI / DeepSeek / Gemini / Claude | `openai:` / `deepseek:` / `gemini:` / `claude:` | 雲端 |

- **雲端模型**：不佔用本地 GPU → 不取得互斥鎖，以背景任務（create_task）**並行**執行。
- **本地模型**：必須取得 GPU 資源 → 依優先權佇列順序、於互斥鎖保護下**串行**執行。

此設計使雲端搜尋、雲端分析等任務可與本地推論並行，充分利用雲端算力；同時保證本地 GPU 不致超載。

### 6.3 實施例二：動態模型降級（F4）

本地模型推理失敗進入重試流程時：

1. 第 1 次嘗試：使用原始指定模型。
2. 第 2 次嘗試起：自動切換至預設之「快速模型」（QUICK_MODEL，通常為更小、更快之模型）。
3. 快速模型成功 → 仍以原回呼函式回傳結果，對使用者無感；僅於內部日誌記錄降級事件（含 latency_ms 追蹤）。

功效：GPU 負載高或模型異常時，系統以「略降品質但不中斷服務」之方式維持回應即時性。

### 6.4 實施例三：群組話題萃取與遺忘機制（F5）

**（A）萃取**：每累積 N 則（例：50 則）真人訊息，系統讀取頻道歷史訊息，交由輕量語言模型（VIBE_MODEL）輸出 JSON 陣列，每一元素含話題名稱（topic，≤15 字）與一句話描述（summary，≤30 字）。

**（B）強化（Reinforce）**：話題已存在時權重重設為上限（例：10）並更新摘要；新話題以權重 2 建立。

**（C）衰減（Decay）**：以定時任務（例：每小時）遍歷所有話題逐一扣減權重，歸零即刪除；頻道話題全數歸零時移除該頻道紀錄。模擬人類遺忘曲線，使陳舊話題自動淡出，無需人工維護。

**（D）注入**：生成對話提示詞時，僅選取權重高於門檻（例：≥5）之話題，依權重排序取前 K 個（例：3 個）注入系統提示詞，使 AI 接得上現行話題。

**（E）原子性落盤**：話題庫寫入採「暫存檔 + os.replace() 原子替換」，程式異常終止不致寫入半毀損資料。

### 6.5 實施例四：AI 主動插話時機評估引擎（F6）

1. **觸發**：每累積 M 則（例：10 則）真人訊息觸發一次評分。
2. **評分**：抓取頻道近期對話快照，結合動態人設提示詞，交由分類器模型（CLASSIFIER_MODEL）輸出「參與吸引度」分數（1–10）與一句理由（JSON 格式）。
3. **決策**：分數 ≥ 門檻（例：7）且未在冷卻時間（例：30 秒）內、且連續插話次數未達上限（例：3 次）時，方生成插話內容。
4. **隨機化**：插話生成提示詞中加入隨機「語氣指令」（salt），避免口吻固定。
5. **反跳針**：提示詞強制不得重複先前使用之詞彙、句型或開場白。

### 6.6 實施例五：長期記憶萃取與深夜整合

- **事實萃取**：由每次對話之 LLM 回覆中萃取使用者事實，每一事實帶權重；權重達門檻（例：≥4）標記為「永久」不被淘汰；超過每用戶上限（例：15 筆）時淘汰最低權重者。
- **深夜摘要（Nightly Digest）**：每日固定時間（例：凌晨 3 點）掃描當日聊天日誌，送較強模型精煉摘要，更新記憶庫。
- **動態注入**：每次對話將最相關之 K 筆（例：5 筆）使用者事實注入系統提示詞。

### 6.7 實施例六：語音對話管線（VAD → STT → LLM → TTS）

- **VAD**：以 Silero VAD 偵測發話端點（語音閾值 0.5、最短靜音 500ms、最長錄音 30s）。
- **STT**：以串流式 ASR 模型（Nemotron-3.5 ASR）轉錄為文字。
- **LLM**：轉錄文字進入 6.2 之推理排程器。
- **TTS**：以 XTTS-v2 語音克隆模型合成回應語音。
- **VRAM 協調**：語音模式啟動時，依 F2 互斥機制暫停圖片生成等顯存任務；語音結束釋放。

## 七、申請專利範圍草稿（Claims Outline）

### 7.1 主案獨立請求項（方法項）

1. 一種多模型 AI 推理排程方法，應用於一資源受限之運算環境，其包含：

   接收複數推理任務，各該推理任務具有一任務類型及對應於該任務類型之一優先權權重；
   將該等推理任務放入一非同步優先權佇列，依該優先權權重之順序分派；
   判斷各該推理任務所對應之模型係一本地模型或一雲端模型；
   對於該雲端模型對應之推理任務，以背景並行方式執行而不取得一資源互斥鎖；
   對於該本地模型對應之推理任務，取得該資源互斥鎖後序列化執行；
   其中該資源互斥鎖係以一非同步事件（Event）實作：於一顯存佔用任務開始時清除該事件、於該顯存佔用任務結束時設定該事件，使等待中之推理任務以事件通知喚醒，而非以輪詢方式等待。

### 7.2 主案附屬請求項（方法項）

2. 如請求項 1 之方法，其中該本地模型對應之推理任務執行失敗時，於重試達一預定次數後，將該推理任務之模型切換為一快速模型。
3. 如請求項 1 之方法，其中該優先權權重係依任務類型設定，被動回覆任務具有最小權重，背景分析任務具有較大權重。
4. 如請求項 1 之方法，其中判斷模型為本地或雲端係依該模型名稱之一前綴字串決定。

### 7.3 分案一獨立請求項（話題萃取）

5. 一種群組對話話題萃取與遺忘方法，其包含：累積預定訊息數後，以語言模型自群組對話萃取複數話題並賦予各話題一權重；當一話題再次被萃取時，將該話題之權重提升至一強化上限；以一預定時間間隔週期性扣減各該話題之權重，於權重降至一門檻值時刪除該話題；以及將權重高於一注入門檻之話題注入後續對話之提示詞。

### 7.4 分案二獨立請求項（插話時機）

6. 一種 AI 對話之主動插話時機判斷方法，其包含：累積預定數量之群組對話訊息後，以一分類語言模型對一對話快照輸出參與度評分；於該評分大於一預定門檻、且距上一次插話超過一預定冷卻時間、且連續插話次數未達一上限時，產生一插話內容。

## 九、替代與變形實施方式

- **平台**：不限於 Discord，可應用於任何支援擴充機制之即時通訊平台（Telegram、Slack、LINE）或自行開發之 Web Chat。
- **推理後端**：不限於 Ollama / LM Studio / vLLM，凡具備 OpenAI 相容或原生 API 之本地或雲端模型皆適用。
- **受限資源**：不限於 GPU/VRAM，可推廣至 CPU 執行緒、共享記憶體、NPU 等有限運算資源。
- **話題萃取**：可改用更輕量之模型或無 LLM 之統計方法（TF-IDF、關鍵字聚類）替代萃取，惟 LLM 萃取可保留語意與內部梗。
- **事件互斥**：可擴充為支援多組資源群之事件陣列，或與傳統鎖混合使用。

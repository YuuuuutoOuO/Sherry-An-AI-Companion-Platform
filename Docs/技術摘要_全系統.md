### 2.4 Micro Chain-of-Thought (Micro-CoT)

- **啟用控制**：`MICRO_COT_ENABLED = True`（`settings.py`）
- **運作方式**：每次 CHAT 回覆前，LLM 先輸出 `<thought>...</thought>` 內心推理區塊，再由 `_process_micro_cot_extraction()`（`handlers/social/utils.py`）抽離並寫入 `runtime_log.jsonl`
- **對使用者隱藏**：thought 區塊不輸出給 Discord 用戶，僅作內部審計用途

### 2.5 Prompt 注入技術

- **動態人設**：`build_dynamic_persona()`（`handlers/social/persona.py`）依對話情境組合 `head_persona` + `tail_lore`
- **氛圍注入**：`get_top_topics_snippet()` 將頻道當前話題注入 Prompt
- **記憶注入**：最相關的用戶事實（最多 5 筆）注入 System Prompt
- **Web 即時檢索**：`fetch_web_and_entity_context()` 整合網路搜尋結果注入 Prompt
- **多模態圖片理解**：支援以 `data:image/jpeg;base64` 傳遞圖片給視覺模型（`minicpm-v`）

## 3. GPU 推理最佳化 (KV Cache / n_batch) ⭐重點

### 3.1 KV Cache 駐留 (Ollama Prompt Caching)

- **設定參數**：`OLLAMA_KEEP_ALIVE = "60m"`（`settings.py` 第 148 行）
- **實作位置**：`handlers/bot_brain/client.py` → `_request_ollama_api()` 中，每次推論請求時將 `keep_alive` 參數傳入 Ollama API
- **運作機制**：
  - Ollama 收到 `keep_alive: "60m"` 後，推論完成**不會立即卸載模型與 KV Cache**
  - 模型與 System Prompt 的 **KV 快取向量保留在 VRAM** 中
  - 下一個請求進來時，Ollama 檢測 System Prompt 未變 → **直接跳過 Prefill 階段** → 大幅降低首字延遲（TTFT）
- **格式支援**：`"60m"`（60 分鐘）、`"24h"`（24 小時）、`"0"`（立即卸載，完全停用快取）
- **硬體條件**：需足夠 VRAM 容納模型 + KV Cache；建議 RTX A4000 (16GB) 以上

### 3.2 n_batch (Prompt 批次處理量)

- **設定參數**：`LLM_NUM_BATCH = 2048`（`settings.py` 第 144 行）
- **實作位置**：`handlers/bot_brain/client.py` → `_request_ollama_api()` 中傳入 `num_batch` 給 Ollama API
- **運作機制**：
  - 對應 llama.cpp 的 `-b` / `n_batch` 參數
  - 控制 GPU 在 Prefill 階段**單次平行處理的 Prompt Token 數量**
  - 預設 512 → 提高至 2048–4096 可**顯著降低首字延遲**（Token 批次更大 = 平行度更高）
  - 代價是 VRAM 峰值略微上升（但 RTX A4000 16GB 足以承受）
- **最佳實踐**：配合 `OLLAMA_KEEP_ALIVE="60m"` 使 System Prompt 不需反覆 Prefill，再搭配 `n_batch=2048`，實現**接近零 Prefill 延遲**的即時聊天體驗

### 3.3 生成參數防跳針

| 參數 | 值 | 作用 |
|------|-----|------|
| `LLM_TEMPERATURE` | 0.85 | 稍高隨機性，避免輸出過於死板 |
| `LLM_PRESENCE_PENALTY` | 0.6 | 抑制已出現過的 token，促進新話題 |
| `LLM_FREQUENCY_PENALTY` | 0.6 | 抑制高頻 token，防重複生成相同內容 |

## 5. 記憶系統與深夜整合

### 5.1 使用者記憶 (user_memory.json)

- **儲存格式**：JSON — 每位 Discord 使用者一個事實列表（`user_id → [{fact, weight, permanent}]`）
- **注入數量**：`MEMORY_MAX_FACTS_IN_CONTEXT = 5`（每次對話最多注入 5 條相關事實）
- **每用戶上限**：`MEMORY_MAX_FACTS_PER_USER = 15`（超出時淘汰最低權重事實）
- **永久記憶門檻**：`MEMORY_PERMANENT_FACT_THRESHOLD = 4`（權重 ≥ 4 自動標記為永久，不被淘汰）
- **實作**：`handlers/memory/` — 由 BotBrain 推理結果中提取事實並儲存

### 5.2 社交關係 (user_relations.json)

- 獨立於事實庫的社交資料：好感度、關係等級等
- **實作位置**：`handlers/social/`

### 5.3 深夜記憶整合 (Nightly Digest)

| 參數 | 預設值 | 說明 |
|------|--------|------|
| `NIGHTLY_DIGEST_HOUR` | 3 | 凌晨 3 點觸發（台灣時間 UTC+8） |
| `NIGHTLY_MAX_MSGS_PER_USER` | 200 | 每用戶送入 LLM 的最大訊息數 |
| `NIGHTLY_MIN_MSGS_THRESHOLD` | 5 | 觸發門檻：當日至少 N 條訊息 |
| `NIGHTLY_DIGEST_MODEL` | PRIMARY_MODEL | 使用較強模型整合 |
| `NIGHTLY_DIGEST_TIMEOUT` | 120 秒 | 整合任務逾時 |

- **運作方式**：每日定時掃描 `chat_logs/` 日誌 → 送 LLM 進行精煉摘要 → 更新 user_memory.json
- **實作**：`handlers/memory/nightly_digest.py`

### 5.4 Context 管理

| 參數 | 預設值 | 說明 |
|------|--------|------|
| `CONTEXT_HISTORY_LIMIT` | 30 | 注入 LLM Prompt 的最大對話輪數（USER+BOT 各算一輪） |
| `CONTEXT_TIME_GAP_SECONDS` | 900 (15 分鐘) | 訊息間隔超過此值 → 視為對話斷層，截斷歷史 |

### 5.5 世界記憶 (world_memory.json)

- `WORLD_MEMORY_PATH`：跨對話的世界級知識（如角色設定、地點）

## 6. 氛圍萃取 (Vibe) 系統

- **實作**：`handlers/vibe_manager/`

### 6.1 核心機制

| 參數 | 預設值 | 說明 |
|------|--------|------|
| `VIBE_UPDATE_MESSAGE_THRESHOLD` | 50 | 每累積 50 則訊息觸發話題萃取 |
| `VIBE_TOP_N_TOPICS` | 3 | 每次取前 3 個主要話題注入 Prompt |
| `VIBE_MIN_WEIGHT_TO_INJECT` | 5 | 低於此權重的話題不注入 Prompt |
| `VIBE_REINFORCE_MAX_WEIGHT` | 10 | 話題再出現時的權重上限 |
| `VIBE_DECAY_INTERVAL_SECONDS` | 3600 (1 小時) | 衰減檢查間隔 |
| `VIBE_DECAY_AMOUNT` | 1 | 每次衰減扣減的權重值 |

### 6.2 技術特點

- **話題萃取**：每 50 則訊息 → 掃描 channel.history → 送 VIBE_MODEL (llama3.2:3b) 輸出 JSON 陣列
- **話題強化 (Reinforce)**：已存在話題重設為 `VIBE_REINFORCE_MAX_WEIGHT`，新話題以 weight=2 建立
- **話題衰減 (Decay)**：`tasks.loop(seconds=3600)` 每小時扣減所有話題權重，歸零自動刪除，模擬遺忘曲線
- **原子性落盤**：`.tmp` 暫存檔 + `os.replace()` 原子寫入，避免寫一半損壞
- **舊版遷移**：`migrate_entry()` 自動將純 int 值遷移至新版 `{summary, weight}` 結構

### 16.2 健康監控
